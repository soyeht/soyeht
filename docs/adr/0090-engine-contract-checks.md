# ADR 0090: The engine checks its events and results against the contract

- Status: accepted
- Date: 2026-10-16

## Context

The engine built almost every event and result by hand with `json!`. The generated models of
`contracts/protocol.json` (`PaneTurnEndedEvent` and about 560 more) were used only by the
round-trip test of the protocol vectors. `Core::publish` took a method name and a `Value`, so
a renamed or misspelt field compiled, passed the engine's tests, and reached the clients as a
missing or ignored field. The first run of the checks below found several such gaps in the
existing code (listed under Consequences).

## Decision

**A check, off in a shipping build.** `soyeht-protocol` has a cargo feature `contract-checks`.
With it, `soyeht_protocol::contract` offers `validate(schema, &Value)`, `event(name, &Value)` and
`result(method, &Value)`. A value is decoded into the generated type of its schema and
encoded again. It fails when the type refuses it (a missing or mistyped field, an unknown
enum value) or when the round trip loses something the engine wrote: a field the contract
does not have, or an optional field sent as `null`. The big `match` over every schema is
generated by `contracts/generate.py` (`src/contract/roundtrip.rs`) and replaces the test-only
`tests/support/dispatch.rs`; the vectors test uses the same function.

**One feature on the engine.** `soyeht-engine/contract-checks` turns it on. Without it the
checks are empty functions and nothing is validated, so a release build does nothing extra.
With it, `model::notification` (every event on the wire, live or replayed), `Core::publish`
(every event, even with no subscriber) and `model::response` (every result, which now takes
its method) return an internal error and write one `engine.contract_mismatch` line naming the
event or method and the reason. The error is a value, not a panic: a request fails, a
connection closes, and a test or an end-to-end run that sees it fails.

**The merge gate runs with it.** In both tiers `scripts/check_all.sh` lints with and without the
feature and builds the workspace with it (the end-to-end scripts start those binaries); it runs
`cargo test` with it (the changed crates in the fast tier, the workspace in the full one). What that covers, exactly:
- A mismatch in a request or in an event published for one fails the request, so the test or the
  end-to-end step that made it fails.
- A mismatch in a background publication fails no request and leaves one log line. The engine
  integration rig (`tests/support/mod.rs`) writes each engine's log to its data directory and
  fails the test when the log, or a rotated file of it, holds `engine.contract_mismatch`. The
  end-to-end `Services.close` does the same.
- Not covered: the `soyeht-cli` and `soyeht-mcp` tests that start an engine themselves, which
  see request failures only.

The shipping configuration is tested as well: the gate runs the test that says an unchecked
build validates nothing, and the two timing meters, without the feature, so they do not measure
a build that decodes every event under the Core lock.

**Typed events.** The generator also emits, for each event, the struct the engine builds
and the trait `EventParams` that names its event. A durable event gets its `eventId`, `at` and
`actor` from the store, so its struct is `...Draft`, without them (an `actor` the schema requires,
as a task movement does, is kept). A live event is built as its own type. `model::pending`
turns one into the `(name, params)` pair the store takes. Eleven of the busiest pane events are
converted: `pane.turn_ended`, `pane.queued`, `pane.config_failed`, `pane.config_changed`,
`pane.state_changed`, `pane.updated`, `pane.created`, `pane.closed`, `pane.auth_finished`,
`pane.session_started` and `pane.permission_answered`. The rest are converted when their
code is touched, except the three that cannot have a type: `pane.update` (its params are a
union of nine update kinds) and `pane.queue.paused` and `pane.queue.resumed` (they share one
params type, so a type could not name its event). The generated code lists them. `scripts/check_event_literals.py` holds the number of
`json!` literals with a `"paneId"` key in the engine (41 now) at its
baseline, which can only fall.

## Consequences

- A misspelt or undocumented field fails the first test that publishes it.
- The first run found these differences between the engine and the contract. Each is fixed on
  the side that was wrong:
  - Every durable event carries the `actor` of its mutation (the store adds it, and contract 08
    already said `actor?`), but 58 event schemas did not declare it. They do now.
  - `pane.update` for terminal output carries `exitCode` (the stored `TerminalOutput` has it);
    the update schema did not. It does now.
  - `pane.permission_answered` from the web permission path had no `paneId`, which every client
    decoder requires. It has it.
  - `harness.list` sent `environmentIssue: null` and `task.list` and `task.comments` sent
    `nextCursor: null`, where the schemas say the field is absent without a value. They leave it out.
  - `pane.update` of kind `system_message` (a blocked permission request) carried neither
    `text` nor `complete`, so a client could not decode it as an `AgentMessageUpdate`. It carries both.
  - `pane.state_changed` carried a `generation`, and `pane.queued` an `addedPromptId`, that no
    schema or client has. They are gone.
  - The `response:writing.structure` vector lacked the required `wordCount`; the vectors of
    events and responses are now checked against their schemas too.
- Adding `actor?` and `exitCode` regenerates the Swift and TypeScript models with optional
  properties; no client reads them yet, and the Swift initialisers default them to `nil`.
- A new engine event is built from its `...Draft` type, or checked at run time; both fail on
  a drift.
- The Linux and Windows engine scripts do not enable the feature yet.
